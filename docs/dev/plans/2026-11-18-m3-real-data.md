# Milestone 3 — real data in the app

Date: 2026-11-18. Approving this plan authorises **Milestone 3 only**. Earlier plans: `docs/dev/plans/2026-11-18-project-plan.md` (M1, roadmap) and `docs/dev/plans/2026-11-18-m2-read-only-core.md`. This plan is copied to `docs/dev/plans/2026-11-18-m3-real-data.md` in Stage 0.

## Context

M1 built the Library screen on mock data, and M2 built the read-only Rust core (`discovery`, `scan`, `icons`) and checked it against the user's real folders. M3 connects the two. When the desktop app opens, it shows the user's real profiles, mods, health issues and icons, and reflects the game's real state.

The browser build keeps the mock data for design review. M3 is still read-only towards game files: switching profiles (M4), copying, moving and removing (M5) and updates (M6) stay inert.

## Outcome (acceptance criteria)

1. **First launch.** `npm run tauri dev` shows the three real folders (`mods`, `$testingMods`, `$offlineTestingMods`) as profiles. The rail shows the right mod counts, sizes and issue counts. `$testingMods` is marked ACTIVE and `mods` is marked as the game default.
2. **Library.** Selecting a profile lists its real mods: titles, authors, versions, types and icons in list and grid. Issues are worded from `src/strings.ts`, including detail lines such as "Copy of FS25_AgroForests". "Also in" lists the other profiles that hold a mod.
3. **Speed.**
   - First scan of a profile: the loading state shows progress ("Reading 120 of 590 mods").
   - Later launches: data comes from the cache, so only changed files are re-read.
   - Rescan: picks up added, changed and deleted files.
   - Icons: decoded on demand when they scroll into view and cached, so a second launch decodes none.
4. **Live game state.** The header and status bar show the real game version and override state, and whether the game or dedicated server is running. This refreshes every 5 s and when the window regains focus.
5. **Folder actions.** "Add mod folder" (folder picker) adds a profile. "Open folder" and "Show in folder" open Explorer. These are the only new actions; other buttons stay inert.
6. **Clean surroundings.**
   - `npm run dev` in a browser still uses the mock, with its `?mock=` switches.
   - The "Sample data" pill appears only there.
   - No writes outside the app's own data and cache folders. No network.

## Decisions for M3

| # | Decision | Rejected |
|---|---|---|
| 1 | **Every listing is fresh.** Each `listProfiles`/`listMods` re-enumerates the folders (stat only, about 45 ms for 590 zips) and reuses cached records for files whose path, size and mtime are unchanged. "Rescan" is the same call. No file watcher yet (P2). | Showing stale cache until a manual rescan; a file watcher now |
| 2 | **Progress streaming, not partial lists.** `listMods` resolves with the complete, assessed list. A Tauri `Channel` streams `{done, total}` progress for the loading state. Health rules and sorting need the whole folder, and a list that changes under the user's selection is worse than a short wait. | Streaming mod batches into the table |
| 3 | **Two SQLite files.** `library.sqlite` in the app data dir holds user data (the profile registry now; tags, notes and sources later). `cache.sqlite` in the app cache dir holds disposable data (per-mod scan records, thumbnails as PNG BLOBs, keyed by path + size + mtime + scanner version). Deleting the cache is always safe. Uses `rusqlite` with bundled SQLite. | One DB mixing user data and cache; thumbnail files with hashed names (needs a stable hash and orphan cleanup); JSON files |
| 4 | **Thumbnails through a custom protocol.** `ModEntry.icon` is `http://thumb.localhost/<profileId>/<modId>?v=<size>-<mtime>`. The handler resolves the ids to a mod the app already scanned, so it never reads an arbitrary path. It serves from the cache or decodes on a worker thread. `loading="lazy"` means only visible icons decode. | The asset protocol with a filesystem scope; pre-decoding every icon during the scan |
| 5 | **Commands take ids, not paths.** The frontend never sends a filesystem path. Rust resolves profile and mod ids through the registry and the last scan. That covers folder opening, reveal, thumbnails and scans. | Path arguments from the frontend |
| 6 | **Profile registry.** On first run it is seeded from `discovery::suggest_profiles`. On every start the effective mods folder and the game's `mods` folder are added if they exist and are missing. The name is the folder name, and the id is a short stable string (`p<rowid>`). Rename and remove-from-list come in M5. | Asking on first run; registering only the active folder |
| 7 | **Errors are codes.** Commands fail with `ApiError { code, detail }` (`profileNotFound`, `folderMissing`, `folderUnreadable`, `internal`), and the frontend words each code in `strings.ts`. | English messages from Rust |
| 8 | **Preferred language** comes from the game log's `Language:` line, falling back to `en`. A settings choice comes later. | Hard-coded English |

## Contract changes (`crates/fsmm-core/src/model.rs` → `npm run gen:types`)

- `ScanProgress { profile_id, done: u32, total: u32 }`.
- `ApiError { code: ErrorCode, detail: Option<String> }` and the `ErrorCode` enum (decision 7).
- No changes to `ModEntry`, `Profile` or `GameStatus`. `icon` now carries the protocol URL.
- `container::IconLocation` and `IconKind` gain serde derives so cache rows can store them (not exported to TS).

`src/api/index.ts`, the `Api` interface:
- unchanged: `getGameStatus()`, `listProfiles()`;
- `listMods(profileId, onProgress?)`;
- `addProfile(): Promise<Profile | null>` (opens the folder picker; null when cancelled);
- `openProfileFolder(profileId)`, `showModInFolder(profileId, modId)`;
- `readonly sampleData: boolean`.

## Architecture

**`fsmm-core` (pure Rust, tested with temp dirs):**
- `store`: opens and migrates both SQLite files. A `schema_version` row plus a numbered migration list. Profile registry CRUD. Mod-record cache get/put by (path, size, mtime, `scan::SCAN_VERSION`). Thumbnail get/put. Prune of rows whose path no longer exists in a scanned folder.
- `library`: the orchestration, testable without Tauri. It owns a `Store` and the last scan per profile, and provides:
  - `ensure_profiles(user_dir, effective, default)` — seeding and the decision 6 additions;
  - `list_profiles()` — scans every registered profile using the cache, fills counts, `is_active` and `is_game_default`;
  - `list_mods(profile_id, progress)` — enumerate → cache lookup → `read_mod` in parallel for misses → cache put → `assess` → `also_in` across profiles by mod name, case-insensitively → icon URL;
  - `thumbnail(profile_id, mod_id)`;
  - `add_profile(path)` and path lookups for open and reveal.
- Path equality: case-insensitive with normalised separators and no trailing separator. The log writes `/` and settings write `\`.

**`src-tauri` (thin):**
- `main.rs` registers state, commands, the `thumb` protocol and plugins.
- `commands.rs` holds one `async` command per `Api` method, each running core work in `spawn_blocking`. `get_game_status` calls `discovery::game_status(&WindowsProbe)`.
- `thumbs.rs` holds the protocol handler.
- Plugins (Rust-side use only, so no frontend capability entries): `tauri-plugin-dialog` (folder picker) and `tauri-plugin-opener` (open folder, reveal file).
- CSP `img-src` adds `http://thumb.localhost`.

**Frontend:**
- `src/api/tauri.ts` implements `Api` with `invoke` and `Channel` from `@tauri-apps/api` (new dependency). `client.ts` picks it when running inside Tauri, otherwise the mock.
- `App.tsx` polls `getGameStatus` every 5 s and on window focus, separately from the profile load.
- Wiring:
  - `ProfileRail`: Add mod folder.
  - `LibraryScreen`: Open folder; progress in `LoadingRows`; Rescan.
  - `Inspector`: Show in folder; issue details worded per kind through new `strings.issueDetail` functions.
  - `StatusBar`: sample-data pill only when `api.sampleData`.
- Error codes are worded through `strings.errors`.
- The mock emits data details, not sentences, and implements the new methods (add returns null; open and show do nothing).

## Verification

- `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace`; `npm run check`; `npm run gen:types` leaves no diff after committing.
- **Real app, read-only** (`npm run tauri dev`, screenshots of the window via `orca computer`):
  - every acceptance criterion above;
  - list and grid, with real icons, at the default window size and at 960×600;
  - inspector on a conflict copy and on a twin;
  - add-folder picker opens and cancels cleanly;
  - Open folder opens Explorer.
- **Timings, logged by the app in debug builds:**
  - first launch vs second launch for `list_profiles` and `list_mods(mods)`;
  - thumbnails decoded on first view vs served from the cache on the second launch.
- **Safety:**
  - Compare the three mod folders before and after a session using a listing of name, size and mtime; they must be unchanged.
  - `gameSettings.xml` mtime unchanged.
  - The app writes only under its own `%APPDATA%` and `%LOCALAPPDATA%` folders.
- **Grid smoothness with real thumbnails:** checked by eye while scrolling the real `mods` grid. The M1 frame measurement used the browser, which has no real data, so this stays a visual check and is reported as such.
- Report what was run separately from what was only inspected.
